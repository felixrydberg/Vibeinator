# Durable information contract

VIB-003 defines the shared records in [durableInformation.ts](../packages/contracts/src/durableInformation.ts), schema fixtures and repository invariants. VIB-004 implements [archive storage and historical backfill](NATIVE-ARCHIVE.md) in migration 142. VIB-005/006 connect adapters; VIB-007 enforces capture-before-publication. Summary, objective and packet repositories arrive in their assigned issues. Shared definitions do not mean those later features already work.

## Ownership and durability

SQLite remains authoritative for conversation text, objectives, normalized events and durable information metadata. `orchestration_events` is the normalized event history; its projections are rebuildable. Native captures are immutable evidence alongside that history, not a second editable transcript. `provider_runtime_events` remains a bounded operational journal with its existing session consumers and cursors. Archive retention must not depend on that journal surviving pruning.

Retain the existing WAL, `foreign_keys=ON`, `synchronous=NORMAL`, exclusive connection ownership and database lifecycle lock. The chosen guarantee is atomic committed transactions across a **process crash**. An OS crash or power failure can lose recent commits not yet synchronized to disk; power-loss durability is not promised. FULL synchronization would need a separate measured decision. A successful SQLite commit does not establish that a provider accepted a command. This issue's reopen tests are not abrupt-crash or power-cut qualification.

One transaction publishes a payload descriptor, all its chunks and the owning record. Nothing may reference an uncommitted or partially written payload. Hash/length conflicts fail the write; disk failure preserves the last committed record. VIB-007 must block new dispatch and stop active work when required capture fails, without retrying external provider execution. Keep existing persist-before-dispatch receipts, cancellation and unknown-acceptance recovery.

## Identity, bytes and normalization

| Record        | Identity and rules                                                                                                                                                                                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture       | App-generated `captureId`; unique tuple `(projectId, threadId, provider, providerInstanceId, runtimeSessionId, lifecycleGeneration, ingressOrdinal)`. The session fields live under `identity.session` in the contract. Allocate the ordinal once at ingress and reuse it for storage retry. |
| Native IDs    | Session/event/item/turn IDs are opaque nullable metadata, never global keys. Providers, accounts, sessions and lifecycle generations can reuse IDs. Repeated identical text at different ordinals is separate evidence.                                                                      |
| Archive order | Database-assigned positive `captureSequence` orders committed captures globally. It is independent of runtime-buffer and orchestration sequences. Allocate it transactionally with publication; gaps are permitted.                                                                          |
| Payload       | App-generated `payloadId`, encoding, UTF-8 byte length, SHA-256 and chunk count. Chunks use `(payloadId, index)` plus byte offset, byte length and SHA-256. Empty content has one empty chunk. Full content has no preview-length cap.                                                       |
| Normalization | Unique `(captureId, eventId)` links allow many captures per event and many events per capture. Link to durable event ID/sequence and optional app turn/message IDs, never just a runtime buffer row. Message identity is `(threadId, messageId)`.                                            |

Idempotency compares the complete immutable envelope and payload bytes/hash under the accepted identity, excluding allocation/commit bookkeeping. An identical retry returns the existing IDs and sequence. Changed bytes or immutable metadata under that identity are a conflict, not an overwrite. Native ID or content-hash equality alone never deduplicates captures. A retry after a failed transaction reuses its ingress identity; a new process/runtime incarnation receives a new app runtime identity and lifecycle generation.

`utf8-text` is the exact observed string encoded as UTF-8 without trimming, Unicode normalization or newline conversion. Valid Unicode round-trips unchanged. JavaScript lone surrogate code units must be preserved through a JSON string payload (`utf8-json`), not silently converted to U+FFFD. `utf8-json` is the exact serialized JSON document accepted at the capture boundary; serialize a decoded SDK object once before shaping, then retain those bytes rather than reserializing on retries. Reject unrepresentable/cyclic/non-JSON objects. This is not a promise to recover the provider's original transport whitespace when the SDK supplies only decoded objects. Hash the stored bytes. Reassemble ordered BLOB chunks before UTF-8 decoding; a chunk boundary may split a multibyte character. Verify offsets, contiguous indexes, total length and hashes on reads. Byte ranges are half-open and must lie inside a verified payload; they do not use JavaScript string indexes.

Envelope version `1` is separate from `payloadType`, which is open-ended. Unknown provider payload types remain retainable as complete text/JSON with provenance even if no normalized event exists. A schema/envelope version the reader does not support must fail explicitly. Existing pruned or clipped content cannot be reconstructed: backfills in VIB-004 must record coverage (`native-complete`, `normalized-only`, or `unavailable`) and the known starting sequence/time, without claiming old previews are complete native captures.

## Capture exclusions and attachment boundary

Adapters must exclude known authentication exchanges and credential material **before** archive, operational logging or derived publication. This includes login/token exchange payloads, access/refresh/API tokens, authorization headers, session cookies, credential-bearing environment/config records and MCP OAuth secrets. Exclude an entire credential-bearing protocol envelope when retaining only part would misrepresent it. Persist only the exclusion envelope and allowlisted reason (`authentication-exchange` or `credential-material`), with safe protocol identity/type and the capture-policy version. No raw payload, payload hash, secret values or free-form diagnostic reason belongs in that record. Identity/type metadata itself must come from allowlisted protocol fields, not an auth response body. Auth-status/approval decisions with no credentials remain ordinary evidence; exclusions must not suppress application approval state. VIB-005/006 must test each provider's credential-bearing shapes as well as unknown benign types.

The archive contains conversation and tool content, which may itself include user-pasted sensitive text. Protocol credential exclusions are not a guarantee of detecting arbitrary secrets inside that content. Repository text, imported history and provider output remain untrusted data; neither a retained source nor a classifier can grant permissions or bypass project boundaries. Exact-payload access requires the existing project/capability authorization, and archive text must never be copied into diagnostics.

**Attachment decision:** image, uploaded file, browser artifact and other binary attachment bytes stay in the existing managed file store. VIB-004 retains SQLite metadata/references including owner, original name, MIME type, known hash/length and availability; it does not migrate every binary into SQLite. Full conversation/tool text and complete objective text remain in SQLite. Provider payloads containing inline base64 data stay complete in their native payload; do not strip it merely because an equivalent managed file exists.

Retain reference metadata after the managed file expires, is explicitly deleted, or becomes missing. Never claim unavailable bytes can be recovered from a reference. Resolve files through the existing managed store and authorization, not an arbitrary archived path. Current managed-file expiry/deletion policy remains in force; the archive adds no indefinite file pin. A SQLite-only backup restores the textual record and attachment metadata, **not** external attachment bytes. A complete attachment backup requires a consistent copy of managed files while the app is stopped. Missing integrity metadata on old attachments stays null. This scope supersedes any reading of “SQLite source of truth” as promising every artifact byte is in SQLite.

## Sources, revisions and packets

`InformationSource` points to a durable capture (optionally a verified byte range), normalized event (ID and sequence), or full objective revision. Repositories resolve every source inside its declared project and chat scope; validating a schema alone does not authorize a source. Capture-only sources need not invent a normalized event. No durable source may point only to a preview, temporary objective file, projection row, or prunable runtime event.

`InformationWatermark` is a pair of independent orchestration and archive sequence high-water marks, scoped by the owning project/chat record. Compute a consistent cut after required normalization is caught up. Processing a high sequence does not imply that earlier pending/unmapped sources were consumed. Candidates record their exact sources and cut; commits advance only through fully considered scoped ranges. Capture excluded/unknown/unavailable coverage explicitly rather than silently skipping it. A packet records the cut actually selected, even if summary watermarks are older.

| Record              | Transaction and replay invariants                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Objective revision  | Immutable, numbered per chat, complete text payload with no delivery-size cap (`utf8-text`, or a `utf8-json` string to preserve lone surrogate code units); previous revision, status and source evidence. Revision 1 has no predecessor. Oversized materialized provider files are derived artifacts mapped back to this revision. Superseding/completing an objective does not prune its text. Historical file-only objectives are marked unavailable if the original file is gone.    |
| Retention candidate | Scope, nonempty source set, source cut, category, decision, classifier/version and retry state. Source text never changes because of classification. Explicit objective/status changes always retain. Uncertain candidates stay pending until consumed; consumed candidates identify the committed revision. Deduplicate by scope, trigger event, source cut and classifier version, not source text.                                                                                    |
| Summary revision    | Separate project and chat streams. Immutable numbered revisions, expected previous revision, text capped at 8,000 JavaScript UTF-16 code units, source citations, processed cut, provider/account/model provenance and time. Empty initial summaries are valid, with null generation for deterministic initialization. Failed/cancelled attempts create no successful revision or watermark advance.                                                                                     |
| Handoff packet      | Immutable prepared packet, app conversation/project and reserved fresh target runtime identity, provider/account/model, actual source cut, summary/objective revision IDs, ordered recent `(threadId, messageId)` pairs, applied limits/reserved overhead, omission counts and summary-refresh state. Store exact context as text and exact sanitized provider dispatch input as JSON payloads with hashes, before dispatch. Preserve nonsecret approval/runtime settings in that input. |
| Packet outcome      | Append acceptance/failure/uncertainty by packet, command receipt and attempt. Native session ID may not exist when preparing the packet; bind the eventual native ID through its outcome/session directory. A later reconciliation appends an outcome; it cannot modify the prepared packet or automatically resend an uncertain command.                                                                                                                                                |

Summary repositories must atomically compare the previous head, append revision/citations, mark only included candidates consumed and move that scope's head/cut. Two writers using the same predecessor cannot both commit. Project and chat heads never overwrite one another. A failed compare-and-swap retries from a newly read head; it cannot silently merge by last write. Source ownership and cut consistency are checked inside that transaction.

Packet limits are measured in JavaScript UTF-16 code units, distinct from archive byte lengths. The later deterministic builder must verify actual rendered lengths against the provider allowance and reserve overhead; descriptor byte length alone cannot prove a character budget. Select recent messages newest-first, then render chronologically with revisions frozen at preparation time. `recentMessages` records selection; exact immutable context/dispatch payloads remain authoritative if message projections later change. A source arriving after the cut must trigger revalidation or be explicitly recorded as omitted before sending. Stored tool calls are evidence only and are never replayed for execution.

## Additive migration and deletion contract

The pinned lineage ends at **141**; VIB-004 registers **142, DurableNativeArchive**. Future migrations must derive the next ID from `LATEST_MIGRATION_ID` at implementation time, register it statically in `Migrations.ts`, and pass `bun run migrations:check`. Never edit released migrations or fill historical slots. Preserve historical tracker aliases and reconciliation. New migrations must tolerate the existing replay path without resetting heads, cursors, objectives, payloads or command receipts. Retain original Synara names in historical tracker rows.

New archive tables own their durable parents. Do not foreign-key archive content to rebuildable `projection_*` rows, prunable operational rows or managed-file cleanup rows. Payload chunks reference their durable payload parent; normalization links reference retained captures and durable orchestration events. Candidate/summary/objective sources and packet revision references must have relational link tables with checked foreign keys, rather than unchecked IDs hidden only inside JSON. Keep project/thread ownership columns and validate membership transactionally against the authoritative event-derived ownership under the engine's write boundary. Avoid migrating old projects/chats into a second independently editable owner registry.

Use `ON DELETE RESTRICT` for referenced payloads, source events and revisions; only payload-to-chunk ownership may cascade after all references are removed by an explicit purge. Projection rebuild, soft archive, operational pruning, objective replacement and provider disposal do not delete durable information. Deletion/purge must invalidate affected candidates, summary heads and packets in one reviewed transaction before removing their source edges; it must never leave a usable summary citing deleted content. Old immutable revisions remain inaccessible tombstones until explicit purge. Project relocation keeps the app project ID and information history, revalidates filesystem access, and never rewrites sources by path. A rollback in conversation history invalidates later derived heads/candidates and prepares a fresh packet from the selected cut; it does not execute historical tools or mutate an already sent packet.

## Upgrade and backout procedure

1. Stop the desktop/backend and confirm the lifecycle lock is released. For an explicit Synara import, copy the database and required managed files to a separate Vibeinator home; never upgrade the source home in place. Preserve a verified pre-upgrade copy.
2. Open the copy with the new binary. Keep the existing pre-migration backup, provenance, recovery marker and free-space checks. Migrations run transactionally under database ownership before providers/background writers start. Disk-full/failure keeps the previous backup and blocks normal startup; use the existing bounded resume/recovery path.
3. Verify tracker, `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, conversation text/IDs, objective coverage and attachment availability. Do not point a second instance or an old binary at the live database for inspection. Use a stopped copy or the existing backup tooling.
4. If schema compatibility changed, stop the new binary and restore the verified pre-upgrade database with the retained offline `restoreMigrationBackup.ts` tool and provenance (see its `--backup-path` / `--provenance-path` usage). Restore a matching managed-file backup when needed. Keep the failed/newer copy for investigation. Only then open the old binary on a separate home. Work committed after that backup is absent from the restored copy; never delete tracker rows to force a downgrade.

The current runner's `MigrationSchemaTooNewError` rejects an exact known lineage followed by newer migrations before writable repositories start. Contract-only VIB-003 has no schema change, so it needs no data downgrade. A future additive migration still requires backup-based backout because an older binary deliberately refuses its too-new tracker; “additive” does not mean “safe to bypass the version guard.”

Each fixture seeds the same synthetic project/chat, long Unicode message, attachment reference, normalized event, accepted receipt, turn, pending approval and native resume cursor, plus a long objective when that schema supports it. Future migrations must keep these fixtures frozen and run them through the new latest migration.

To regenerate a fixture intentionally, export that revision's `apps/server/src/persistence` tree into workspace scratch storage, execute its `runMigrations()` against an empty temporary database, and dump noninternal `sqlite_master` DDL plus `effect_sql_migrations` rows. Do not copy seeded application/auth data. Keep source SHA, exact migration names and deterministic tracker timestamps. Review schema changes before replacing a frozen fixture; do not regenerate old fixtures merely to make a failing new migration pass.

Validation commands: `bun run --cwd packages/contracts test src/durableInformation.test.ts`, `bun run --cwd apps/server test src/persistence/DurableMigrationFixtures.test.ts src/persistence/Migrations.test.ts src/persistence/Migrations/MigrationReplay.test.ts src/persistence/MigrationBackup.test.ts src/persistence/NodeSqliteClient.test.ts`, then workspace formatting/lint/type checks. Binary packaging, live provider crash tests and power-loss behavior are outside this contract issue's evidence.
