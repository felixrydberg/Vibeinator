## Area

packages/contracts or packages/shared

## Problem or use case

Full-content retention, provenance and packet semantics need shared definitions before different features invent incompatible stores.

## Proposed solution

Define the records/invariants in the storage section, native-to-domain identity mapping, capture exclusions, attachment policy, complete objective revisions, and additive migration ownership. Build synthetic databases at the pinned schema and representative released schemas; never read personal databases for tests.

## Why this matters

Keep complete project context available across restarts and provider handoffs while extending the retained Synara implementation.

## Smallest useful scope

Upgrade/backout procedures are written; foreign keys and replay behavior are specified; identities handle multiple providers and repeated native IDs; unknown payload types remain retainable. Tests prove pre-existing conversations survive migrations and an older binary refuses a too-new schema. Decide process-crash versus power-loss durability explicitly.

## Alternatives considered

Reuse the existing Electron app and provider integrations; a framework migration or provider rewrite is outside this plan.

## Risks or tradeoffs

Priority: P0. Dependencies: 001. Estimate: 1–2 days.

Preserve existing conversation data, approval boundaries and provider lifecycle behavior. Additive schema work must follow the migration contract and include recovery evidence.
