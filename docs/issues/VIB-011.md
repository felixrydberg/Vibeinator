# [Feature]: VIB-011 — Classify completed-turn information into durable candidates

GitHub: https://github.com/felixrydberg/Vibeinator/issues/11

## Before submitting

- [x] Searched existing repository issues; no duplicate implementation step found.
- [x] Concrete implementation step from the agreed Vibeinator plan.

## Area

apps/server

## Problem or use case

Extract useful information for later rewriting without copying every message into summaries.

## Proposed solution

Subscribe at successful coding-turn boundaries, read bounded source sections, classify retention/category, and persist source IDs and pending candidates. Always include explicit goal/objective/status changes. Distinguish coding turns from maintenance turns so classification cannot recursively trigger itself.

## Why this matters

Keep complete project context available across restarts and provider handoffs while extending the retained Synara implementation.

## Smallest useful scope

Duplicate completion events produce one candidate set; failures/interruption follow documented retention rules; unavailable Clef conservatively retains pending candidates. Retries/restart do not skip source ranges. Source text remains immutable and complete irrespective of classification.

## Alternatives considered

Reuse the existing Electron app and provider integrations; a framework migration or provider rewrite is outside this plan.

## Risks or tradeoffs

Priority: P1. Dependencies: 005, 006, 009, 010. Estimate: 1–3 days.

Preserve existing conversation data, approval boundaries and provider lifecycle behavior. Additive schema work must follow the migration contract and include recovery evidence.
