## Problem or use case

## Proposed solution

Measure startup subscriptions, periodic jobs, dependencies and unwanted UI paths. Candidate areas include extra providers, Hubs, automation/device integrations and marketing build participation. Disable or remove one independently owned feature per PR only after checking contracts, dynamic references, migrations and tests.

## Why this matters

Keep complete project context available across restarts and provider handoffs while extending the retained Synara implementation.

## Smallest useful scope

A measured cost or clear product exclusion justifies each removal, required behavior remains qualified, and retained history/schema remain readable. Record actual removed code/dependencies and performance changes. No blanket deletion percentage or reactor rewrite is a prerequisite for shipping.

## Alternatives considered

Reuse the existing Electron app and provider integrations; a framework migration or provider rewrite is outside this plan.

## Risks or tradeoffs

Priority: P2/optional. Dependencies: 019 and measurements. Estimate: Re-estimate from evidence.

Preserve existing conversation data, approval boundaries and provider lifecycle behavior. Additive schema work must follow the migration contract and include recovery evidence.
