# Native archive storage (VIB-004)

Migration **142, `DurableNativeArchive`**, implements storage behind the [durable information contract](DURABLE-INFORMATION.md). It adds no renderer surface or provider protocol change. [Codex](CODEX-CAPTURE.md) and [Claude](CLAUDE-CAPTURE.md) connect owned coding sessions in VIB-005/006, with the documented credential exclusions and limits. VIB-007 integrates shared durable projection/replay and dispatch-readiness guarantees. These tables do not imply complete capture of every provider or historical traffic.

## Repository and encoding

[NativeArchiveRepository](../apps/server/src/persistence/Services/NativeArchive.ts) is an internal Effect service. Its [SQLite layer](../apps/server/src/persistence/Layers/NativeArchive.ts) shares the application's existing owned connection and supports nesting inside a caller's event transaction. Providers can use `appendCapture` at their native ingress boundary; repositories for objectives and packets can use `appendPayload`. No operation executes a provider command.

| Operation                            | Guarantee                                                                                                                                                                                                                                                                                                        |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `appendCapture`                      | Database-generated archive sequence, app-generated capture/payload IDs, immutable identity/content fingerprint and idempotent storage retry. Reused native IDs across providers, accounts and session lifecycles do not collide. Credential exclusions have metadata and an allowlisted reason, with no payload. |
| `appendPayload`                      | Stable caller-owned key within a project/chat. Descriptor and all 64 KiB BLOB chunks publish in one transaction. Same key/encoding/bytes returns the original descriptor; changed content fails with an identity conflict.                                                                                       |
| `readPayloadPage` / `streamPayload`  | At most 16 chunks (1 MiB) per page. Check ordered indexes, offsets, byte lengths and chunk SHA-256; the stream verifies the full length/hash before completing. Consumers must observe completion rather than treating a partial stream as a complete payload.                                                   |
| Capture/link/source/attachment lists | Explicit exclusive cursors and limits of 1–100 records. Capture reads use an explicit inclusive sequence fence. Normalization links verify durable event ID/sequence and thread ownership; referenced events/payloads cannot be pruned accidentally.                                                             |
| Scope                                | Reads require a surviving, nondeleted project/chat ownership match. Archived chats remain eligible. Wrong-project or deleted targets return no records; writes reject them. Transport capability checks remain the caller's responsibility; no public history RPC is added here.                                 |

Callers submit exact well-formed UTF-8 text or an already serialized JSON document. JSON is validated but not reformatted. JSON string encoding preserves lone surrogate code units; direct text with an unpaired surrogate is rejected rather than silently replaced. Embedded NUL, Unicode, whitespace and newlines remain complete in BLOB content. Database identity/key columns require valid Unicode without NUL; opaque native metadata inside the JSON envelope remains unchanged. Provider-specific credential exclusions must happen before calling the repository, at the adapter boundary specified in VIB-005/006.

The repository exposes typed validation, ownership, identity-conflict, integrity and storage failures. Errors do not include SQL parameters, payload text or driver causes that might disclose content. SQLite disk-full can roll back automatically and cause the SQL client's subsequent rollback to defect; the archive converts that failure into its storage error channel while preserving cancellation. A failed call is not permission to execute or re-execute a provider command. Abort the owning transaction on any archive failure; do not catch it and continue writing inside that transaction. Reconcile storage through the same accepted identity; future capture callers must stop dispatch/publication until durable acceptance is established.

## Tables and retention

`durable_payloads` / `durable_payload_chunks` retain complete content. `native_captures` and `native_normalization_links` retain native identity and durable event provenance. `durable_legacy_sources` binds surviving historical evidence; `durable_capture_coverage` records the historical cut. `durable_attachment_references` retains managed-file metadata and availability. `durable_archive_backfill` stores finite migration fences and committed progress.

None of these records depends on a prunable runtime row or a foreign key to rebuildable projections. Payload references and normalization/event references use restrictive foreign keys. The runtime journal keeps its existing consumer/checkpoint/open-turn retention behavior; pruning it does not delete archive content. Projection repair and ordinary session disposal do not reset the archive.

Existing **explicit thread purge** removes archive edges, captures, payloads/chunks, coverage and attachment metadata in the same transaction that removes the thread's normalized events and projections. This preserves the meaning of deletion and prevents foreign keys from blocking the existing purge. Automatic runtime retention does not invoke that archive purge. Future summary/packet repositories must extend the same purge transaction with their own source edges before shipping.

## Historical backfill

Database setup finishes a resumable backfill before exposing writable services or starting provider/event consumers. Migration 142 freezes event, message, goal and managed-attachment row fences once. Pages contain at most 50 source records and load one large message body at a time; retained records and the page cursor commit together. A failure leaves earlier pages committed and rolls back the current page. Reopen resumes at that cursor. Completed phases are inert, including after migration replay. Large old histories can make the first upgrade slower; there is no recurring full-history scan.

- Existing normalized thread events stay in `orchestration_events`, protected by durable source references. They are not copied into a second editable transcript.
- Surviving message projections become immutable JSON snapshots in chunked payloads. Backfill reuses the existing message-text assembly helpers to join JSON fallbacks and ordered streaming chunks, preserving NUL and unmatched UTF-16 code units. Legacy TEXT bodies are read as BLOBs to avoid Node 24 truncating surviving content after NUL. Snapshot metadata retains attachments and other message fields.
- Inline goals become complete JSON string payloads. Historical materialized-goal paths remain references marked **unavailable / external-objective-not-imported**; migration does not follow untrusted paths or symlinks. Even an existing external file is not claimed as imported. Durable objective revision integration and safe recovery of those old files remain goal work under VIB-017.
- Coverage is `normalized-only` when surviving normalized evidence exists, otherwise `unavailable`. It never claims previously clipped/pruned native data was recovered. Excluded/unmapped native capture coverage will be established by the later adapter capture path.
- Binary attachment bytes retain their managed-file lifecycle. Historical references without a managed blob are conservatively `missing`; known metadata stays available for inspection. Managed upload/cleanup transitions update retained availability, and tombstone compaction does not erase it. Availability reflects managed-store lifecycle, not a new filesystem scan; no binary bytes are moved into SQLite or pinned indefinitely.

A SQLite-only backup contains textual archive content and attachment references, not external file bytes. Upgrade/backout continues to use the existing pre-migration backups and too-new-schema refusal. Migration 142 is additive and replay-safe; do not remove its tracker row to force an old binary to open it.

## Verification

The focused archive tests exercise multi-megabyte text/JSON, byte boundaries, empty payloads, duplicate concurrent appends, conflicts, exclusions, cross-project/deleted-thread isolation, source foreign keys, disk-full and read-only failures, cancellation, corruption and operational pruning/reopen. Backfill tests cover resumable page rollback, frozen fences, legacy Unicode chunks, missing external objectives and attachment cleanup. Historical schema fixtures from v0.5.5, v0.6.7 and the pinned revision now run the backfill as well as migrations. An explicit purge test exercises the existing stats-preserving deletion service with retained archive evidence.

A real Bun SQLite subprocess round-trips archive content. A second synthetic Bun writer calls `process.exit(23)` while a WAL transaction remains open, before the Effect transaction finalizer; reopen must retain the prior committed capture and publish none of the staged capture. This qualifies the tested SQLite writer-exit case. External process-tree termination, power loss, provider crash recovery and signed packaged behavior remain unqualified. WAL/NORMAL's OS-crash/power-loss limitation remains unchanged.

CI runs the focused storage/recovery tests on Windows and Linux before the broader inherited test suite. The latter has known baseline failures; passing archive tests do not imply a green full suite or complete native capture integration.
